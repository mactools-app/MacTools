# General Voice Assistant tasks

Voice Assistant combines existing plugin actions with general computer tools. A task needs no app-specific recipe: the backend observes a running app, chooses a native menu, keyboard or control step, observes the effect, and continues until the goal is complete or blocked. Existing plugin actions remain preferred when they directly express the goal.

Enable Computer interaction and Allow reading app content in Voice Assistant settings. The latter remains device-local setup consent. The selected control mode admits ordinary UI steps in its listed running applications for at most five minutes and forty input steps. Reads include those apps' visible windows and app-wide native menus. In Ask first mode, a button confirmation names the goal and applications and explains that app commands and data changes are possible. Direct control uses the user's saved local opt-in instead of showing routine cards. Task approval never expands the conversation's plugin grants.

## Tool protocol

These canonical actions use the existing discovered-capability bridge and host executor.

The existing voice/backend connection follows OpenAI's [GPT-Live tool continuation flow](https://developers.openai.com/api/docs/guides/live-delegation). This layer supplies composable local tools and task state without introducing another model service.

At conversation startup, local host discovery exposes the allowed general task capabilities as typed backend functions, each mapped to its actual host-issued session ID. These use the existing canonical host executor and approvals, without a second dispatch path or SDK change. Discovery creates no API session or app-content read by itself. The session also reports missing computer-interaction, app-reading-consent or Accessibility setup. A chooser is not a substitute for a requested app effect; when setup is missing, explain how the user can enable it instead of opening a manager or bypassing consent with a command.

| Action | Behavior |
| --- | --- |
| `computer-task-begin` | Admit a goal and JSON array of running app names/bundle IDs; return task and app IDs pinned to process lifetimes. |
| `computer-task-observe` | Read running state, windows, Cua controls and one native menu level. `menuPath` selects an observed submenu path. |
| `computer-task-step` | Perform one `menu`, `key`, `type`, `click`, `set-value`, `scroll` or bounded `wait` step. Consume a unique step ID before dispatch. |
| `computer-task-finish` | End with `completed`, `blocked` or `cancelled`. Completion requires observing after the final input; the backend must judge that observation against the whole goal. |
| `computer-command-start` | Admit a concrete command, directory and timeout under the selected control mode for a managed background session. |
| `computer-command-status` | Read bounded stdout/stderr, truncation, running state and eventual exit code. |
| `computer-command-cancel` | Cancel the owned process group; poll status to confirm it stopped. |

Every input needs an observation of the exact window within thirty seconds and consumes that observation, including uncertain writes. Menu IDs are single-use, expire after thirty seconds and are re-resolved against native menu objects. Menus are read one level at a time. Window-context menu input focuses and verifies the requested window immediately before pressing the item. Keyboard input checks process lifetime, window focus and an unprotected focused element, then posts to that PID. Letter/digit shortcut names resolve against the selected keyboard layout, including Command-specific layouts; Shift, Option and Control remain explicit modifiers. The layout is rechecked before dispatch. Text inserts at the selection. Cua continues to handle native control reads, clicks, writable-field replacement and scrollbar actions with its existing policy checks.

An app without a visible window can still expose its native app menus: observation uses window ID zero for that app-menu context. Menu operations can create a first window or quit the app; keyboard/control input still requires a real, freshly observed window. Each task also limits total observation data to 256 KB, in addition to its step/time limits, and command-status polls wait briefly for completion to avoid a tight API loop.

This uses in-process Apple APIs without enabling Cua's automatic scripts, helpers, global-input or pixel fallbacks. Screenshot/vision interaction is not included in this version; custom canvases without suitable accessibility, menus or keyboard behavior may need user interaction. MacTools' own windows remain excluded, including its consent UI.

## Commands and cancellation

Host 2.2.4 adds the optional `PluginVoiceConfirmationPresenting` companion, without changing released voice-context layouts or protocol witness tables. Voice requests use the floating assistant's approval card or its locally selected Direct control mode; older consumers retain the host sheet. The canonical executor still binds the exact parameters and context and rechecks admission after approval. Enabling automatic access for future plugins remains a button decision.

Direct control is an explicit, device-local setting, initially off. Enable it while no conversation is running to execute requested actions and commands without routine approval cards. It applies only during active conversations and stays subject to allowed features, setup consent, system permissions, concrete target/parameter checks and task budgets. The setting persists on this Mac, is excluded from portable backups and cannot be changed by voice. The panel displays the enabled mode; turning it off ends the current conversation and owned work. Existing in-memory conversation/process scopes are not migrated into this opt-in.

With Direct control off, Ask first uses one Allow/Cancel card in the assistant. The microphone gate pauses input while the card is pending and advances its audio generation on presentation and resolution, discarding old buffered PCM. Calls begun during approval stay blocked even if their backend result arrives after the card closes. Cards expire after 45 seconds; Stop or cancellation declines them. There is no separate spoken-confirmation recognizer or transcription charge. Silero remains the local connect-on-speech detector. Model arguments and captions cannot grant permission. Setup changes such as enabling automatic access for future plugins always require their own button decision, including in Direct control mode.

The backend may propose a command for an explicit user goal. In Ask first mode the card shows the actual command, directory and deadline. In both modes admission binds that exact request and the opened directory identity, following normal macOS directory aliases. The runner uses an open directory descriptor, a minimal environment excluding inherited API keys, `/bin/zsh -f`, noninteractive stdin, a dedicated process group and bounded output. PluginKit's process-group lease prevents cleanup from signaling a reused PID. Commands and output remain in memory and are not saved as scripts. Natural leader exit retires the execution deadline before bounded descendant cleanup, so cleanup cannot relabel completed work as a timeout.

Managed commands run in the background. If Terminal or another terminal window was requested, use that app's approved UI task: create a new session through observed menus/shortcuts, type the command and send Return. Do not silently substitute background execution. Continuous commands need an agreed duration or later cancellation. Commands must not daemonize or leave their managed process group. Cancellation is best effort: a command already accepted for execution may start or finish before cancellation reaches it.

The panel has one Stop control. It immediately ends the conversation, stops microphone capture and playback, revokes the host session and its issued IDs, cancels queued/awaiting host requests, and requests cancellation of owned native work and commands. The panel stays visible. Late replies from the old connection are ignored for actions, captions and playback, including responses whose first event arrives after Stop. Only final usage accounting may drain briefly before that connection closes. Restart requires an explicit Start Conversation and a fresh host grant.

While current work settles, the control shows Stopping for up to one second. The work row remains visible with cancellation requested, current operation completed, remaining steps cancelled, or an uncertain operation that may still be finishing. Already-started effects cannot be undone, and cancellation never claims that nothing ran. If cleanup exceeds the short window, Start Conversation becomes available with the uncertain notice retained; an explicit restart clears that old notice, and late cleanup cannot change the new conversation. Owned command jobs remain tracked through process cleanup even after their old command IDs are revoked. Finishing a UI task restores progress for any remaining command. There is no separate Stop Task button.

Admissions carry a revocation generation rechecked when lazy execution begins. Dismissal, lock, sleep, feature disablement and read-consent revocation use the same Stop path; dismissal also hides the panel. UI text and command output are untrusted data, never authorization or instructions.

## Qualification

Host 2.2.4 distinguishes executable actions from interface navigation. Pure picker/panel/preview actions declare `ActionExecutionCapabilities.opensInterface`; discovery publishes them as `kind=feature`. The ordinary `perform_capability` tool refuses these before opening any UI. Explicit `open_interface` requests still use the canonical executor and report `interfaceOpened`, which is not a completed application operation. This applies to Quit Apps, Launchpad, Window Switcher, Action Grid, Mac Settings navigation/previews and System Status, without adding app-specific quit handlers.

Providers may implement the additive `PluginVoiceFunctionProviding` companion. Discovery carries validated `voiceFunctions` names keyed by host-issued IDs in its JSON payload. Names describe existing canonical actions; they do not expose undeclared actions or supply permission. Voice Assistant publishes `computer_task_begin`, `computer_task_observe`, `computer_task_step`, `computer_task_finish` and `computer_command_*` at startup. Invalid, duplicate or reserved function names cannot redirect a tool call. Legacy hosts without the sidecar retain opaque bootstrap names; the updated plugin requires host 2.2.4. Released v7 capability layouts and witness tables remain unchanged.

Focused tests cover concrete approval, process/window scope, fresh observations, replay rejection, late results, expiry, output/exit status, cancellation and environment isolation. An owned AppKit fixture checks real selection and Unicode insertion, discovered menu effects and normal app termination, recording effects independently of accessibility readback. These establish tool-layer behavior; live voice planning and acceptance in user apps are separate checks.

A bounded backend planning check also uses the actual tool definitions and backend instructions against the disposable fixture. Its test bridge permits only the fixture and a fixed harmless command; native approval is simulated within that test scope. It verifies planning and native effects without claiming live microphone, user-app or production approval acceptance.
